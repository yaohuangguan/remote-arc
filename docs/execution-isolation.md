# 执行隔离：能力现状与后续决策

状态：设计建议，未实现隔离执行器或 Dashboard 沙箱开关。
审查依据：PR41 / PR43 / PR44，截至 2026-10-01。

## 决策

保留默认本机执行，不把现有路径检查命名为沙箱。建议后续独立实现可选的
隔离执行配置，优先满足运行不可信仓库、安装依赖和无人值守高权限命令的需求。
它不是长任务持久化的前置条件，也不是 PR44 本次文档与首页改造已经交付的能力。

Remote Arc 的主要价值是访问用户已有的电脑、仓库、依赖和工具链。强制把所有
工作迁入隔离环境会改变路径、运行时、凭证、开发服务器端口和硬件访问方式。
对可信的自有项目，默认本机执行有实际用途；对不可信代码或希望更严格限制
副作用的工作，则需要独立的 OS 执行边界。

## 什么是沙箱隔离

沙箱应在执行点由 OS 或独立虚拟环境强制限制：可见/可写目录、进程和设备、
用户身份、凭证、网络出站与资源用量。命令里的绝对路径、符号链接、子进程或
网络请求不能绕过这个边界。提示词要求“只修改项目”、检查 cwd 或匹配危险
命令字符串都不等同于这种隔离。

AI 宿主自己的沙箱不自动覆盖远端 MCP 动作。宿主通过 Remote Arc 调用目标
电脑的 `start_process` 时，真实 OS 操作发生在目标电脑，而不是宿主沙箱中。

## 当前已有的防护

| 边界 | 实际保证 | 不保证 |
| --- | --- | --- |
| OAuth / ownership / revocation | 授权客户端只访问所属账户和未撤销设备 | 不隔离已获准执行的 OS 用户 |
| Allowed tools / `--safe` | 控制是否允许读、编辑、终端等工具 | 终端被允许后的任意命令隔离 |
| Trusted Write Locations + Approval Broker | 普通非敏感文件可只读查看；受支持的持续写入限制在可信写入区域，越界写入在执行前请求窄范围审批；终端需要范围内 cwd | Shell 仍可引用范围外路径、凭证、子进程或网络，因此不是 OS 沙箱 |
| Sensitive Path Policy | 文件工具保护敏感位置并支持窄例外 | Shell 内部文件访问拦截 |
| Safety Guard | 拒绝有限灾难性命令模式，纵深防护 | 任意脚本分析或完整命令沙箱 |
| Task contract / policy snapshot | 冻结目标、工具和限制，策略变化停止旧任务 | OS 内部所有副作用或回滚 |
| Local Undo | 受支持文件工具编辑的冲突安全恢复 | Shell、数据库、部署、发布等回滚 |

实现证据：`packages/execution-core/src/core.ts`、`policy.ts`、`process.ts`，
`apps/relay/src/device-call.ts`、`device-task-policy.ts` 和 `automations.ts`。
进程执行使用 `spawn(..., { shell: true, cwd, ... })`，继承当前本机用户权限。
未发现 namespace/container/VM/AppContainer 等 OS 沙箱执行路径。

## 现阶段怎么用

- 只需读取和文件编辑的设备保持终端关闭；普通非敏感读取可以保持灵活，长期修改使用 Trusted Write Locations，偶发越界写入走 Approval Broker，敏感路径继续独立保护。
- 需要命令但希望减少可访问内容时，使用专用受限 OS 用户和最少凭证。
  受限用户是 OS 权限边界，不能被称为通用命令沙箱。
- 需要隔离运行不可信代码时，配对用户自己管理的隔离 VM/机器/环境，并正确
  配置它的文件、凭证和网络边界。不要把宿主文件系统或特权控制接口全部暴露进去。

容器不是天然的“安全开关”。Docker 官方文档说明守护进程控制、权限配置和
挂载会影响隔离；可写 bind mount 可以修改宿主内容。
参考：[Docker Engine security](https://docs.docker.com/engine/security/)、
[Bind mounts](https://docs.docker.com/engine/storage/bind-mounts/)。

## 未来产品形态

建议在 Dashboard → Devices 配置执行环境，而不是增加没有执行器支持的开关：

| 配置 | 用户理解 | 状态 |
| --- | --- | --- |
| 本机执行 | 使用当前电脑的工具与 OS 用户权限 | 当前实现 |
| 隔离执行 | 使用已验证隔离环境，只暴露明确目录与能力 | 未来提案 |

设备上报执行器类型、版本、实际可用隔离边界和限制。只有探测成功时才可选隔离。
Task 合同冻结执行配置、映射目录、网络/凭证授权与资源限制。创建后不能静默
降级为本机执行；隔离器不可用、配置变更或重启丢失时，停止或等待，并记录原因。

未来隔离执行器中的文件工具和终端必须观察同一个隔离映射，避免 Agent 读取本机文件却在容器
修改另一个副本。`process_id`、日志、停止、验证和恢复都必须属于所选执行器。
输出同步应有明确确认策略；不要把自动复制宿主敏感文件作为便利功能。

第一阶段可考虑用户提供的 Linux 容器/隔离设备适配，验证目录、非特权用户、
无宿主控制 socket、明确网络策略、资源限额和进程树清理。Windows/macOS
需要分别验证实际执行器与运行时兼容性，不承诺“一份命令实现所有 OS”。
容器与 VM 的强度不同，文档应描述实际边界而不是统一宣称绝对安全。

## 上线前的验证标准

1. 目录外读取/写入、符号链接逃逸、宿主凭证、子进程与网络绕过的对抗测试。
2. 受限文件编辑、测试运行、输出读取、进程停止及开发服务的真实工作流程。
3. Pause/Cancel/expiry、设备重连和执行器重启后的恢复；不重复未知副作用。
4. 执行配置改变会使旧合同失效；隔离故障不会回退本机。
5. 每个受支持 OS 的实际权限和兼容性检查，而非仅 mock 测试。

建议作为 PR44 后的独立功能立项。当前文档只解释现状与设计方向，当前 UI
不显示已经拥有隔离能力，也不改变现有设备执行行为。
